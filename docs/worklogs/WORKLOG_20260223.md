# Work Log (OAK-D-PoE + Visual SLAM)

**Date:** 2026-02-23

## Objective of this phase
1. Establish a **stable stereo-only baseline** that meets cuVSLAM input expectations (near 30 Hz).
2. Separate causes between:
   - network/PoE link instability
   - DepthAI driver/device disconnect behavior
   - host-side throughput limits
   - ROS2 discovery/daemon issues
   - VSLAM integration issues (topics, image_transport, TF)

## What we did
### A) Stability and link verification
- Observed intermittent disconnects:
  - `ping was missed`, `X_LINK_ERROR`, `No Data` and image publishing stops.
- Tested NIC-side mitigations:
  - Disabled EEE and offloads (GRO/GSO/TSO/LRO) and confirmed EEE disabled.
  - Result: did **not** fully eliminate disconnects.
- Verified that during some stable runs, NIC counters did not show increasing drops/errors.

### B) ROS 2 discovery / daemon inconsistency
- Found cases where `ros2 topic list` worked but `ros2 node list`/`ros2 param get` failed.
- Restarting the ROS2 daemon (and clearing its cache) restored correct behavior and right-stream observability.

### C) Diagnosis automation
- Introduced a diagnosis script to run a configuration and collect:
  - `ros2 topic hz/bw`
  - `dmesg -w`
  - `ip -s link` / `ethtool -S`
  - docker stats (when available)
  - snapshots on error signatures

### D) Key measurement: resolution vs FPS
- 720p-class streams plateaued around 25–27 Hz for `image_raw` while `camera_info` remained ~30 Hz.
- New **400p stereo-only config** achieved ~30 Hz sustained for both left/right raw and camera_info.

### E) Visual SLAM integration trial
- cuVSLAM initializes, but odometry sometimes does not reflect motion or exhibits large jumps.
- Log patterns include frame timing warnings and image_transport errors (unexpected transport selection).
- Suspected root causes:
  - republish arguments misconfigured (should force raw->raw)
  - camera and vslam in same single-thread component container
  - TF/baseline sign mismatch

## Findings (current)
- The system can deliver stable 30 Hz stereo at 400p.
- Higher resolution stability is likely host-side bottleneck.
- Disconnect recovery is weak (restart often required).
- VSLAM behavior is currently dominated by integration correctness rather than feature scarcity.

## Immediate next actions
1. Fix/validate image transport pipeline:
   - ensure republish is raw->raw, or bypass republish and feed raw directly.
2. Split camera and vslam into separate containers (or use MT executor safely).
3. Validate TF chain and baseline sign.
4. Run vslam on the stable 400p baseline and check odometry sanity.
